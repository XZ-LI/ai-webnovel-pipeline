# 章节诊断与改稿

`$SK` = 本 skill 的 `scripts/` 目录。

写完一章就能查，不用等攒到几十章才发现跑偏。**诊断和改稿是两条命令，中间卡着作者的决定**——按"全部问题都修"去自动重写，往往把本来写得好的段落一起换掉。

## 诊断

```bash
python3 $SK/review_chapter.py diagnose --project "<书名>" --chapter 3 --genre 西方奇幻
python3 $SK/review_chapter.py diagnose --project "<书名>" --last 3           # 最近三章
python3 $SK/review_chapter.py diagnose --project "<书名>" --chapter 3 --mechanical-only
```

省略 `--chapter` 查最新一章。报告写到 `novels/<书名>/reviews/ch003_review.md`（给人读）和同名 `.json`（给改稿用，编号就是 `--fix` 的号）。

### 机械层（不花钱，不会看错）

| 检查 | 判据 |
|---|---|
| 字数越界 | 不在 2600–3600 字之间 |
| 标题格式 | 首行不是「第N章 标题」——发布端按首行取章节名，格式不对线上会缺标题 |
| 技巧标签残留 | 正文里出现「心理——」「长句：」这类写作技巧标签 |
| 段落过长 | 单段超过 180 字，手机上一屏放不下三行就会掉读者 |
| 开篇手法重复 | 与上一章同为对话 / 内心独白 / 动作开篇 |
| AI 味套话 | 叙述里出现套话。铁套话一次就报，常见套话达到密度阈值才报 |

开篇分类只认有把握的三类，认不准就不报——宁可漏也不要误报。

**AI 味这项有两个设计决定值得说明。**

一是**只查叙述，不查对话**。人物嘴里说套话是人物特征（一个爱说"命运如此"的角色是立住了的），
叙述者说套话才是毛病。所以比对之前先把「」""''里的内容剥掉。

二是**分两档**。「时光荏苒」出现一次就该报，它在任何小说里都是偷懒；「然而」「就在这时」
出现一次完全正常，出现六次才是抽动。一刀切会把报告刷满噪音，而作者看两次就再也不看报告了
——那比不报更糟。阈值是 `AI_CLICHE_SOFT_MIN`。

改稿时套话的处理也和技巧标签不同：**技巧标签直接删，套话要替换**。删掉"他心头一紧"
会留一个语义空洞，字数也会掉，补回来的往往是另一句套话；该换成一个具体的动作或生理反应。

词表在 `assets/ai_cliches.txt`，分五类（空洞抒情、万能过渡、万能形容词、情感标签、
动作口头禅），每类带自己的修法，会直接显示在报告里。自己的补充写进同目录的
`ai_cliches.author.txt`，格式一样，不会被任何重建覆盖。

`--mechanical-only` 适合写完一批章节先扫一遍，挑出有问题的再花钱做语义诊断。

### 语义层（一次调用）

按题材模版的质量自检表（10 项带权重）给分，只对 6 分以下的维度报问题；同时**逐条核对 `bible.json` 的 `hard_constraints`**，并找与设定自相矛盾的地方（能力提前到手、死人复活、时间线错乱）。

每个问题都要求**引用正文原句作为证据**，找不到原句就不报。这一条很关键：没有证据约束的评审会生成听起来有道理但正文里并不存在的问题。

同一处问题常被三个通道各报一遍（硬约束、一致性、质量都会说"哑巴开口了"），报告会按证据原文合并成一条，并注明"同一处也被判为 …"。

## 改稿

```bash
python3 $SK/review_chapter.py revise --project "<书名>" --chapter 3 --fix 1,3 --genre 西方奇幻
python3 $SK/review_chapter.py revise --project "<书名>" --chapter 3 --fix all
```

**必须先有诊断报告**，`--fix` 的编号就是报告里的序号。

改稿时会做三件事：
1. 备份原稿到 `chapters/.bak/NNN.txt`（只备份最初那一版，反复改稿不会把它冲掉）；
2. 只针对指定问题改写，并明确要求**情节事实不许变**——本章发生过的事件、出场人物、结局位置都要保留，因为后面的章节已经建立在它们上面；
3. **同步重新生成该章摘要**。这一步不能省：摘要是后面几百章的事实依据，正文改了摘要不改，错的事实会一路继承下去。

退回原稿：

```bash
python3 $SK/review_chapter.py restore --project "<书名>" --chapter 3
```

注意 `restore` 只退正文，摘要还是改稿后那一版——退完要么重跑一次 `revise`，要么手工改 `summaries.jsonl` 对应那行。

## 你（Claude）在这一步该怎么做

- **把诊断念给用户**，不要只给文件路径。每条问题带上证据原句，他才判断得了。
- **让他决定改哪几条**，然后用 `--fix` 点名。不要自己替他 `--fix all`。
- 报告里的得分是相对参考，不是绝对质量承诺。6 分的维度值得看一眼，8 分的不用动。
- 改稿后建议再诊断一次确认——改写可能引入新的越界（比如字数）。
- 同一章反复改稿超过两次还不满意，问题通常不在这一章，而在弧线计划或故事圣经。回到 `method.md` 的"症状 → 改哪一层"。

## 什么不该用改稿解决

- **剧情方向不对**：改 `arc_plan.txt`，或用 `new-arc --variants` 重挑弧线，不要靠逐章改稿把故事拧回来。
- **人物性格一直漂**：那是 `bible.json` 的人物档案太笼统，或者该写进 `hard_constraints`。
- **整本书的文风不对**：换 `--genre` 的题材规则，或往 `assets/prompts/<性别>/<题材>.author.txt` 加规则，见 `genres.md`。

改稿是精修，不是重写。一章要改三处以上的结构性问题，直接删掉重写更省（记得按 `method.md` 的三步回退，连摘要一起退）。
