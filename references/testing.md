# 怎么测这个 skill

四类测试，成本和能回答的问题完全不同。按这个顺序做，便宜的先排除掉大部分问题。

| 类别 | 成本 | 回答什么问题 | 怎么跑 |
|---|---|---|---|
| 1 回归自检 | 免费，几秒 | 改完有没有把已有行为改坏 | `python3 scripts/selftest.py` |
| 2 触发测试 | 很便宜，纯文本 | 用户那么说，skill 会不会被用上 | `python3 scripts/trigger_test.py` |
| 3 行为测试 | 几美元 | 它按不按文档走流程 | 真机跑一遍 + 对照清单 |
| 4 质量测试 | 几美元 | 写出来的东西到底好不好、模版有没有用 | `review_chapter.py` + A/B 对比 |

## 1 回归自检（每次改完都跑）

```bash
python3 scripts/selftest.py        # 失败项才打印
python3 scripts/selftest.py -v     # 连通过的一起列
```

不调任何 API，几秒跑完。覆盖 194 项确定性检查：

- **结构**：15 个脚本存在且语法正确、9 份文档存在、触发测试集有正反两类、描述带排除条款、文档里引用的 reference 真实存在、37×2 份题材资产齐全非空、规则层都带免责声明、**资产里没夹带作者个人信息**（分发前必查）
- **premise 模板**能被 `init` 的解析器吃下（40 个 `=`、`【书本名称】`、章节标题正则）
- **提示词装配**：硬约束置顶、伏笔只渲染未兑现的、超期伏笔有提醒、往事提要超限合并、字数区间进了提示词、摘要只展开最近 N 章、章型带禁止项、hint 不含 `【类型】` 残渣、手写大纲按区间命中、里程碑按上限截断
- **正文清洗**：剥掉「心理——」这类标签、不误伤"他的心理，早已崩塌"、保留段间空行与超短句段落、丢掉纯标点残行
- **伏笔台账**：JSON 解析、代码围栏、非 JSON 兜底、新增/兑现/去重
- **信息边界**：人物档案三种形状都能遍历且可原地改、人名歧义时不猜、单章登记上限、渲染截断、刷新圣经会回填 `knows`、提示词里有禁止条款且无人知情时不占预算
- **AI 味**：词表分两档、对话里的套话豁免、常见套话未达密度不报、**干净样例上零误报**（改词表改出噪音会先被这条拦住）
- **题材解析**：唯一匹配、男女频同名报错、指明性别可用、不存在报错
- **诊断器**：五类机械检查都能抓到、AI 味按分类归并、同一处问题会合并
- **配置层**：服务商预设完整、环境变量优先级、缺 key 时给出明确指引
- **自我一致**：文档里宣传的自检项数等于真实项数（写过 132、实际 163 的漂移就是这么发现的）；生成 agent 入口文件时拒绝盖掉同名的权威指南 `AGENTS.md`（`--force` 也不行）

改了提示词、改了解析逻辑、改了模版生成，跑它。全绿不代表写得好，只代表没坏。

## 2 触发测试（skill 不被用，后面全白搭）

这是最容易被忽略的一类。skill 靠 `description` 决定要不要被加载——描述写不好，用户说"帮我写本小说"它也不会读。

测试集已经造好了，21 条：`evals/trigger_eval.json`（11 条该触发 + 10 条不该触发，每条都标了考点）。

```bash
python3 scripts/trigger_test.py                 # 每条跑 1 次
python3 scripts/trigger_test.py --repeat 3      # 看稳定性
python3 scripts/trigger_test.py --only-negative # 只测不该触发的
```

它把每条提问交给一个**全新的** `claude -p` 会话，看那个会话有没有自己去加载这个 skill，然后分别列出"该触发却没触发"（描述缺覆盖）和"不该触发却触发了"（描述太宽）。花的是 Claude Code 的额度，不是 OpenAI 的钱。

**需要 claude CLI**：`npm install -g @anthropic-ai/claude-code`。没装的话脚本会把 21 条问题打印出来，手动在**新会话**里一条条问，看它第一步是不是读 SKILL.md（当前会话不算，它已经加载过了）。

**不该触发的那些才是重点**。它们和 skill 共享关键词但需要别的东西：

- "给我讲讲网络小说这个行业的商业模式" —— 命中"网络小说"，要的是行业科普
- "我要给孩子讲个睡前故事" —— 命中"想写故事"，但不是长篇连载
- "写个 Python 脚本把 txt 按章节切分" —— 命中"章节"，是写代码
- "这本小说的版权合同该注意什么" —— 命中"小说"，是法务

因为这些近似项，`description` 末尾专门写了排除条款（单篇文章/书评/睡前故事/翻译润色、行业与榜单分析、以及提到小说但其实是写代码的活），判断标准落在一句话上：**有没有一本要持续写很多章的书**。改描述时别把这段删了，不然这四类会开始误触发。

历次实测结果记在 `evals/trigger_baseline.md`，改描述之后拿它对比。2026-10-20 那轮是 21/21，而第一轮是 19/21——漏掉的两条（"第三章读起来不对劲"、"快穿文读者爱看什么"）暴露了一个典型问题：**功能有、入口没开**，诊断改稿和题材知识都实现了但描述里没写。

skill-creator 还带了自动化的描述优化循环（分 train/test、每条跑 3 次、迭代最多 5 轮），要跑就问 Claude "用 skill-creator 优化 novel-pipeline 的触发描述"。

## 3 行为测试（它按不按文档走）

从零跑一遍完整流程，对照这张清单看。每条都有明确的"该发生什么"：

| 阶段 | 该发生 | 不该发生 |
|---|---|---|
| 开口 | 先问题材、手上有多少东西、给谁看 | 直接开始写 |
| 入口 | 你给的那句话被原样传进 `--seed`，方案里写明沿用了什么 | 先替你总结成几个词 |
| 出方案 | 3 个方案的金手指和核心矛盾互不相同 | 同一个故事的三种措辞 |
| 展开 | 格式自检跑了（`【书本名称】`/分隔线/首章字数） | 直接 init 然后建歪 |
| 立项 | **先念 `hard_constraints`** 再念人物和世界规则 | 只报"项目建好了" |
| 试写 | 先写 3 章给你看，问具体问题 | 一次写 20 章 |
| 写完 | 自动登记新埋的伏笔、字数落在 2600–3600 | 字数飘到四千多 |
| 诊断 | 把问题念给你、带原文证据、让你挑改哪条 | 自己 `--fix all` |
| 换弧 | 自动压上一弧提要；要多版本时只写候选不落地 | 直接覆盖当前计划 |

跑完还要查文件层：`novels/<书名>/` 下的 `bible.json`（含 `hard_constraints` 和 `open_threads`）、`arc_plan.txt`、`summaries.jsonl`、`arc_digests.jsonl`、`chapters/`。

**在新会话里跑**。同一个会话里 Claude 已经知道上下文，测不出真实体验。

## 4 质量测试（写得好不好）

### 纵向：同一本书的趋势

```bash
python3 scripts/review_chapter.py diagnose --project "<书名>" --last 5 --genre <题材>
```

看各维度得分随章数的走势。权重 3 的维度（钩子强度、人物鲜活度、悬念设计、世界观融合）连续几章在 6 分以下，说明问题在圣经或弧线计划，不在单章。

### 横向：模版到底有没有用（A/B）

这是整个 skill 最该验的一件事——37 个题材模版是卖点，但得证明它比不用模版强：

```bash
# 同一个 premise 建两个项目
python3 scripts/write_novel.py init --from <同一个premise> --project A
python3 scripts/write_novel.py init --from <同一个premise> --project B

python3 scripts/write_novel.py write --project A --count 3 --genre 西方奇幻   # 带模版
python3 scripts/write_novel.py write --project B --count 3                    # 不带

python3 scripts/review_chapter.py diagnose --project A --last 3 --genre 西方奇幻
python3 scripts/review_chapter.py diagnose --project B --last 3 --genre 西方奇幻
```

两边都用同一张自检表打分才可比。更干净的做法是**复制同一个项目目录**再分别往下写（`bible.json` 和 `arc_plan.txt` 哈希一致），这样 init 的随机性不会混进来，唯一变量就是带不带 `--genre`。

历次结果记在 `evals/ab_baseline.md`。2026-10-20 第一轮是 7.52 vs 7.30，**差值太小、样本只有 3 章，不足以证明模版让整体质量变好**——真正有信息量的是差异的落点：不带模版那组的弱项落在"外形描写"（两次 6 和 5 分），而这条正是模版规则层里明文规定的。

做 A/B 时注意两个坑：一是**确认你比的指标真的受实验变量影响**（字数区间写在通用提示词里，和 `--genre` 无关，不能把字数差异记在模版账上）；二是**评分者偏差**，写和评都用 o3 就是自己批自己作业，同一张表只保证可比性，不消除系统性偏差。

A 级题材（规则经过迭代）和 B 级题材（只有评分维度）也值得这样比一次——能告诉你那 7 个 A 级是否真的值当初那些迭代成本。

### 盲评

诊断器自己打的分有"自己批自己作业"的问题。更硬的做法：把两章正文去掉所有标记，交给另一个会话问"哪一章更想让你读下一章，为什么"。不要告诉它哪章用了什么配置。

**两种顺序各跑一次，这一步不能省。** 实测里两轮都选了"后出现的那一个"——位置偏好。只跑一轮会得出完全错误的结论。两轮选同一位置就说明这次盲评无效，要么换评审、要么加样本。

**看定性批评，不只看结论。** 实测中盲评的胜负是无效的，但它的定性反馈抓到了诊断器完全没发现的缺陷：正文里漏出了一行写作提示「（十五字解释他童年被修女安提娅救，满足动机补位）」。那是题材规则的名字被抄进了正文——**规则越具体，模型越容易把规则本身写进去**，这是用模版的代价，值得专门防。

### 人读

最终还是要你自己读。读的时候盯这几样，它们是自动检查测不出来的：主角说话的腔调是不是一个人、爽点落的位置对不对、读到章末有没有想翻下一页。

## 一个现实的提醒

自检全绿 + 诊断 8 分 + 流程清单全过，仍然可能是一本没人看的小说。这些测试能保证的是**不出技术性事故**（设定矛盾、哑巴说话、字数失控、伏笔失忆），保证不了好看。好看那部分靠你给的设定、你挑的方案、和你读完之后的反馈。
