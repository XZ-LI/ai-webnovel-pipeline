# 这套记忆结构怎么运作，以及出问题时改哪一层

`$SK` = 本 skill 的 `scripts/` 目录。

## 记忆的六层

一本 300 章的书装不进任何模型的上下文，所以每写一章只喂这几样进去：

| 层 | 存在哪 | 内容 | 谁来维护 |
|---|---|---|---|
| 1 硬约束 | `bible.json` 的 `hard_constraints` | "违反即整章作废"的红线 | 人工过目，很少变 |
| 2 故事圣经 | `novels/<书名>/bible.json` | 世界规则、全部人物档案、总走向 | 每 10 章自动据摘要刷新 |
| 3 伏笔台账 | `bible.json` 的 `open_threads` | 埋了还没兑现的东西 + 埋在第几章 | 每章写完自动登记 |
| 4 弧线提要 | `arc_digests.jsonl` | 每弧一段 200–300 字的往事提要 | 一弧写满自动压缩 |
| 5 弧线计划 | `arc_plan.txt` | 当前 30 章的细化规划 | 一弧写满自动生成下一弧 |
| 6 摘要 + 近期原文 | `summaries.jsonl` / `chapters/` | 最近 10 章摘要 + 最近 2 章全文 | 每章写完自动追加 |

进度在 `state.json`：`current_chapter`（已写到第几章）、`arc_number`、`arc_start`。

**注意摘要只有最近 10 章进上下文**（`FORMAT_SUMMARY_RECENT`），更早的折成一行"已压缩入故事圣经"。所以第 10 章之外的记忆，靠的是圣经、伏笔台账和弧线提要这三层——第 3、4 层就是为此补的，没有它们，跨 20 章的伏笔会彻底失忆、200 章的书会散成"一弧一个独立副本"。

## 硬约束：`bible.json` 里最该人工过目的字段

`hard_constraints` 是一个字符串数组，渲染进提示词时置顶成"══ 绝对不可违反的事实 ══"，并在离"开始写"最近的位置再强调一次。只放那种**违反了整章就废**的事实：

```json
"hard_constraints": [
  "主角不能说话。全书不得让他发出声音，台词只能是心声、手势、书写或他人代述。",
  "回应低语必付代价：每次借力都加深理智裂痕且不可逆，不得出现无代价的奇迹。",
  "雷神权能属于第61章之后，此前只能失控或被动承受，不得主动调用。",
  "养母已死并葬在北丘，只能以幻象或回忆出现，不得真正复活。"
]
```

为什么需要这一层：圣经里有几十条设定平铺着喂进去，模型在"把这个场景写顺"的时候会忽略其中一条。实测过的真实事故——主角设定是哑巴，弧线计划给某章的提示里出现"对话"两个字，那一章他就开口说了四次话，而且前后两章对失声原因给了三种不同说法。

写法要求是**可直接检查的断言**："主角不能说话，台词只能用心声或手势"能检查；"人物要有成长"不能检查，不要放进来。

`init` 生成圣经时会自己产出 3–6 条，但**一定要人工过目**——它挑的未必是这本书真正的红线。想加就直接编辑 `bible.json`，下一章立刻生效。

## 伏笔台账

`bible.json` 的 `open_threads`，每条长这样：

```json
{"thread": "铜铃柄能破圣封的原理与来历未解释", "planted_chapter": 6, "status": "open"}
```

维护方式是**搭在摘要那次调用上**，不额外花钱：压缩摘要时同时要模型产出 `new_threads`（本章新埋的）和 `resolved_threads`（兑现了哪些旧的），兑现的条目改成 `status: paid` 而不是删掉。拿不到 JSON 就退回把整段当摘要——台账这一章不更新，但写作不会中断。

渲染进提示词时按埋下的早晚排序（埋得最久的在最前，它们最该被收也最容易被忘），最多常驻 12 条，超过 30 章未兑现的标注"埋了很久，该考虑兑现了"。

**单章最多登记 2 条**（`MAX_NEW_THREADS_PER_CHAPTER`）。实测模型会把每一个还没解释的名词都报成伏笔——一章 5 条，三章就攒出 15 条未兑现，里面混着"截纹灰能扰追踪符尘之说尚未验证""月精针获取途径成谜"这种人物随口提到的小设定。台账很快变成噪音，真正的核心悬念被碎屑稀释。所以提示词里给了判断标准——**三十章后它没有下文，读者会不会觉得被骗**，不会就别登记——程序层再加一道硬截断。

想人工干预就直接编辑 `bible.json`：加一条自己想埋的、把写错的改掉、或把不打算收的直接删除。这是作者该管的事——台账只负责不让它从上下文里消失，不负责替你决定收不收。

## 弧线提要

`arc_digests.jsonl`，一弧一行。每弧写满时自动把那 30 章的摘要压成 200–300 字（一次调用），要求保住四样：主角处境的根本变化、人物登场/死亡/转变立场、长期有效的世界规则与实力设定、还没解决的问题。

渲染成"往事提要（每弧一段，第 10 章之前的事都在这里）"常驻上下文，最多保留最近 8 弧，更早的合并成一行总述。所以 240 章以内每弧都有独立的一段，再往后开始合并。

## 为什么这样切

**硬约束管"碰不得的事"，圣经管"永远为真的事"，台账管"欠着的债"，弧线提要管"很久以前发生的事"，弧线计划管"近期要兑现的事"，摘要和原文管"刚刚发生的事和听起来像不像同一个人写的"**。各层更新频率不同，所以输入量是常数：

| 写到第几章 | 输入 token（tiktoken 实测） |
|---|---|
| 5 | ~18,900 |
| 10 | ~19,800 |
| 50 | ~19,800 |
| 300 | ~19,900 |

第 10 章之后就持平了，写第 1000 章和第 50 章一样大、一样贵。加上台账和弧线提要只多了约 1,300 token。

剩下的膨胀风险在圣经本身：里程碑和人物只增不减。两道控制——渲染层每个人物只取最近 4 条里程碑（`MAX_MILESTONES_SHOWN`），`update_bible` 的提示词也要求旧里程碑合并成一句、走完的环境只留结论。别指望往圣经里塞越多越好，挤掉的是近期原文。

用 `write_novel.py status --project "<书名>" --genre <题材>` 看当前这一章的真实输入 token（实际构造一次提示词再量，不是按公式估）。**要带 `--genre`**，否则算不进题材规则层那 5,300 token。

## 自动化的节奏机制

这些都写在生成提示词里，用户问"为什么这章是感情戏"时能答得上来：

- **章型六循环**：战斗章 → 人物章 → 感情章 → 揭秘章 → 喘息章 → 转折章，按章号轮转。连续同类型章节是长篇最容易垮的地方（十章连着打，读者会腻）。
- **每 5 章一次配角视角**，避免全书被主角一个腔调绑死。
- **防重复扫描**：自动扫最近两章的开篇手法（战斗开篇 / 内心独白开篇 / 对话开篇 / "突然"式反转），把用过的列进提示词要求避开。
- **每章 3000 字上下，允许 2600–3600 字浮动**（`CHAPTER_MIN_CHARS` / `CHAPTER_MAX_CHARS`）。连载按章追更，忽长忽短会打乱读者节奏。只给下界会飘——实测过只写"3000 字以上"时出现过 4917 字的一章。
- **章型指令带禁止项，并且优先于通用要求**。慢节奏章（人物章、感情章、喘息章）明确不许用追逃和战斗凑冲突；题材规则层那几千字"每章必须有冲突/悬念"的通用要求体量压倒性，不写禁止项就会把慢章推成动作戏。
- 摘要上限 150 字。

## 手动干预

```bash
python3 $SK/write_novel.py new-arc      --project "<书名>"   # 重做当前弧计划
python3 $SK/write_novel.py update-bible --project "<书名>"   # 据近期摘要刷新圣经
```

一般不用手动跑——弧满和每 10 章会自动做。只在剧情被人工改动过、或发现圣经跟正文脱节时才手动触发。

**弧线计划也可以先出几个版本再挑**，和立项阶段同一个道理——它要管接下来 30 章：

```bash
python3 $SK/write_novel.py new-arc --project "<书名>" --variants 3
#   → novels/<书名>/arc_candidates/arc<N>_v1.txt … v3.txt
#   arc_plan.txt 和 state.json 都没动
python3 $SK/write_novel.py new-arc --project "<书名>" --use novels/<书名>/arc_candidates/arc3_v2.txt
```

生成时会把前面几个方案的要点塞进提示词要求"主要事件与转折明显不同"，所以三份不会是同一个计划的三种措辞。挑定前把三份的差异念给用户听，别只给路径。

直接编辑 `arc_plan.txt` 和 `bible.json` 完全可以，而且往往比让模型重生成更准：用户说"我想让女主在第 40 章叛变"，就写进弧线计划，不要只在对话里答应。

### 手写逐章大纲

在项目目录里放 `outline_<起>_<止>.txt`（例如 `outline_31_60.txt`），格式一行一章：

```
第31章【雪线之上】：主角在雪线遇到旧敌，被迫交出半块玉符。
第32章【旧敌的交易】：旧敌提出合作，主角假意答应。
```

落在这个区间内的章节会优先用这里的章纲，并且该区间的弧线计划不会被自动生成覆盖——适合用户对某一段剧情有明确要求的时候。区间外自动回落到 `arc_plan.txt`。

## 写坏了怎么回退

模型写出崩坏的一章（人物说错名字、设定自相矛盾、剧情跳线）时，三件事一起做，缺一不可：

```bash
cd novels/<书名>
rm chapters/045.txt                                  # 1. 删正文
# 2. state.json 的 current_chapter 改回 44
# 3. 删掉 summaries.jsonl 的最后一行（下面这句在 macOS/Linux 都能用）
python3 -c "import pathlib;f=pathlib.Path('summaries.jsonl');L=f.read_text(encoding='utf-8').splitlines();f.write_text('\n'.join(L[:-1])+'\n',encoding='utf-8')" 
```

**只删正文最危险**：摘要还在，下一章会把那段崩坏剧情当成已发生的事实继承下去，而且它还会在下次圣经刷新时被写进圣经，变成"全书设定"。

连删多章就重复上面三步，摘要删对应行数。

## 症状 → 改哪一层

| 用户的抱怨 | 根因通常在 | 怎么动 |
|---|---|---|
| 人物性格前后不一致 | 圣经的人物档案太笼统 | 编辑 `bible.json`，把性格写成可执行的（口头禅、底线、怕什么），而不是形容词 |
| 违反了设定的硬事实（哑巴说话、死人复活、能力提前到手） | 那条事实没进 `hard_constraints` | 加进去，措辞写成可检查的断言；下一章立刻生效 |
| 慢节奏章被写成追逃或打斗 | 章型指令被题材规则的通用要求压过 | 已在章型里加了禁止项并声明优先级；仍然跑偏就把具体禁止项写进 `<题材>.author.txt` |
| 章节字数忽长忽短 | 只有下界没有上界 | 已改成区间；要改幅度就动 `CHAPTER_MIN_CHARS` / `CHAPTER_MAX_CHARS` |
| 剧情原地打转、没推进 | 弧线计划太空 | 编辑 `arc_plan.txt`，给接下来 10 章各写一句明确事件 |
| 设定自相矛盾（功法/地理/时间线） | 圣经的世界规则缺项 | 在 `bible.json` 的 `world` 里把规则写死，包括代价和限制 |
| 文风突然变了 | 近期两章本身就是跑偏的 | 回退那两章重写，别指望下一章自己纠回来 |
| 每章读起来都一个样 | 提示词层面的问题 | 用 `--system-prompt` 换整套写作指令（`corpus.md` 讲怎么迭代出一份） |
| 伏笔忘了兑现 | 它没进 `open_threads`，或者进了但一直没人收 | 看 `bible.json` 的 `open_threads`：缺了就手工加一条；在里面躺了 30 章以上的，直接写进弧线计划"第 N 章兑现 X" |
| 很久以前的事它不记得了 | 超出最近 10 章，而那件事没进圣经/台账/弧线提要 | 看 `arc_digests.jsonl` 里那一弧的提要写了没；重要的事实补进圣经 |
| 章节太短/太长 | 脚本常量 `CHAPTER_TARGET_CHARS` | 改 `$SK/write_novel.py` 顶部的常量 |

诊断的顺序永远是**先看最近两章原文，再看弧线计划，最后看圣经**——由近及远，因为越远的层改动代价越大。

## 风格参考（可选）

`--style-dir <目录>` 可以指向一个参考语料库，结构是 `<目录>/<分类>/*.txt`，其中 `<分类>` 要和 `bible.json` 里的 `category` 字段**完全一致**才会命中。命中后会按当前章号从同分类高分作品里取邻近章节做风格样本（只学节奏笔法）。

目录不存在或分类对不上就是没有风格样本，脚本静默继续，不报错——所以如果用户期待风格参考却没生效，先检查这两处对不对。怎么建语料库见 `corpus.md`。
